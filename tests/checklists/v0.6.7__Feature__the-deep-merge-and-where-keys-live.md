## What this is

The second pass of the AI merge. Pass 1 (v0.6.0) let a model pick lines inside the conflict-hunks -- the regions both sides changed -- and never showed it anything else. This pass lets a model read the diff-hunks -- the regions one side changed and git took on its own -- together, in a disposable copy, and write text, as far as a scope you choose allows. It also moves a hosted backend's key into a file under your own territory. The automated tests prove the mechanics on synthetic worlds with the backends faked; the golden set proves nine known-right answers canned. This document is for what they cannot see: what a real model does with the founding case, whether the report's words are the right words on a real terminal, what `--accept` asks when the file is the model's, and what `ccs doctor` and `ccs collect` say about a real key.

## Prerequisites

1. Python 3.12+, git, and this branch installed in editable mode (`pip install -e .`), or run every `ccs` below as `python -m dazzle_claude_config` from the worktree root.
2. **A scratch world, never your real config.** Every command below carries three overrides so nothing touches `~/.claude`, `~/claude` or your payload checkout. Set the root once:

   **cmd.exe**:
   ```cmd
   set SCRATCH=%TEMP%\ccs-deep-checklist
   ```
   **PowerShell**:
   ```powershell
   $env:SCRATCH = "$env:TEMP\ccs-deep-checklist"
   ```
   **POSIX**:
   ```bash
   export SCRATCH=/tmp/ccs-deep-checklist
   ```
3. Build the world. The builder lays out a checkout with two commits (the base, then Charlie's change), a neighbour file and a far file, and a live file holding Bob's change; `--case` picks the shape:

   ```
   python tests/one-offs/thinking/deep-merge/build_deep_world.py "%SCRATCH%" --case python        (cmd)
   python tests/one-offs/thinking/deep-merge/build_deep_world.py "$env:SCRATCH" --case python     (PowerShell)
   python tests/one-offs/thinking/deep-merge/build_deep_world.py "$SCRATCH" --case python         (POSIX)
   ```
   Cases: `python` (the founding case: Bob doubles what `c()` returns, Charlie makes `c()` return a pair), `python-control` (Charlie's `c()` still returns an int), `markdown` (Bob adds a step citing "the report", Charlie renames it "the summary"), `markdown-control`, `conflict` (pass 1's shape, one conflict-hunk). It prints the exact `--checkout-dir/--claude-dir/--user-claude` triple to paste; every `ccs` line below assumes it as `<OVR>`. Add `--no-color` to `<OVR>` when you want to copy output into a report.
4. **LM Studio**, for the free live runs (HV.2, HV.3, HV.4, Section 1, Section 5): the server started from the Developer tab with the one model this box is permitted to load; `ccs <OVR> doctor` says `no model server at http://127.0.0.1:1234/v1` until it is. Nothing in this checklist loads a model.
5. **Scratch-git rules**, in case you make your own commits in the world: every git command carries `-C <scratch path>`, and every commit carries `-c user.email=t@t -c user.name=t -c commit.gpgsign=false -c tag.gpgsign=false` -- on a machine with global signing a bare commit fires a pinentry dialog. Never change global git config.
6. Reset between sections: `dz safedel` the scratch root (or delete it) and rebuild with the case the section names.
7. **Nothing here spends money unless you are in Section 7**, and nothing sends your configuration anywhere except the model you name.

## High-Value Verification (~5 minutes, LM Studio running)

**If you only have 5 minutes**, run these five.

### HV.1 -- A clean merge is not a resolved one

Validates: the founding case's report line -- a merge with no conflict-hunk, run without the deep step, says so and names it.

- [ ] **Steps:** build `--case python`, then `ccs <OVR> merge skills/s.py --ai claude --no-launch`
- [ ] **Expected:** exactly this line, then the ordinary `merged (not installed): skills/s.py` summary; exit 0; nothing is sent to claude (there is no conflict-hunk to send):
  ```
  ai  skills/s.py -- no conflict-hunk; git took the diff-hunks on its own, nothing for the recipe to decide -- add ,deep to read them together
  ```
- [ ] **Check:** `<user>/merge/ccs/skills__s.py.merged` is git's own merge of the two changes -- `b()` doubles, `c()` returns a pair -- and is wrong: `python -c "exec(open(r'<that file>').read()); print(a(3))"` prints `(4, 2, 4, 2)`.
- [ ] **Why this matters:** this is the danger the whole feature exists for. If the line reads as "resolved", the person accepts a broken file.

### HV.2 -- The deep step fixes the founding case on a local model

Validates: the plan, the sandbox, the no-tools form, the ladder verdict, the numbered variant and the report, with a real model and no money.

- [ ] **Steps:** same world, `ccs <OVR> merge skills/s.py --ai lmstudio,deep --no-launch`
- [ ] **Expected:** `steps: lmstudio (recipe), deep via lmstudio -- scope hunk` first; the `no conflict-hunk` line **without** the `-- add ,deep` nudge; then
  ```
  staged skills/s.py -- the AI's answer skills__s.py.merged-ai.1 (deep via lmstudio; needed hunk, hunk allowed); nothing installed
      files touched: 1
      guarantees: this variant may contain text no side wrote; the ladder allowed edits in the changed regions and their surrounding code and every edit landed there (needed: hunk); the loss check ran as a tripwire only; your diff is the gate -- no tools: the model saw this file and the two diffs only
      <the model's one-sentence summary>
      b (rung 1): <the model's reason>
      ccs diff skills/s.py --ai --variant 1 opens it beside yours
  ```
- [ ] **Check:** `ccs <OVR> diff skills/s.py --ai --variant 1` opens the variant beside `.merged` in your diff tool; the only difference is inside `b()`; `python -c "exec(open(r'<the variant>').read()); print(a(3))"` prints an integer or a pair of integers, not `(4, 2, 4, 2)`. **Judge it:** the golden set's answer is `return (v[0] * 2, v[1] * 2)`, but any edit confined to `b()` that makes the two changes consistent is a right answer; write down what this model chose. A model that instead edits `a()` or `c()` gets `NOT KEPT skills/s.py -- the model's edits needed file scope and hunk was allowed -- nothing kept; the edits it would have made are listed` -- that is the ladder working, and Section 1.2 is where you widen it.
- [ ] **Why this matters:** the first time a real model runs the deep step end to end through the command. Everything before this was fakes.

### HV.3 -- The control: nothing to change

Validates: an unchanged file is a correct answer, and is not pending work.

- [ ] **Steps:** rebuild with `--case python-control`, then `ccs <OVR> merge skills/s.py --ai lmstudio,deep --no-launch`
- [ ] **Expected:** `ai  skills/s.py -- nothing to change (deep via lmstudio): the merged file stands`; no `.merged-ai.1`; exit 0.
- [ ] **Judge it:** a model that "fixes" a file with nothing wrong is the failure the golden set's controls exist to catch. Note what it did if it did not say nothing.

### HV.4 -- A scope the backend cannot reach is refused before any call

Validates: the no-tools form's ceiling, said before a byte is sent.

- [ ] **Steps:** `ccs <OVR> merge skills/s.py --ai lmstudio,deep --ai-scope neighbours --no-launch` (either python case)
- [ ] **Expected:** `steps: lmstudio (recipe), deep via lmstudio -- scope neighbours`, the `no conflict-hunk` line, then instantly:
  ```
  ai skipped skills/s.py -- lmstudio has no tools: it can reach rung 2 (file), not neighbours -- pass --ai-scope hunk or file, or use a CLI backend with tools (deep via lmstudio)
  ```
  With the server stopped the line is `backend 'lmstudio' is not available (no model server at ...)` instead -- the readiness check comes first.
- [ ] **Why this matters:** the report must never let a person believe a server backend reached a neighbouring file.

### HV.5 -- `--accept` asks with the deep step's guarantees, and no is the default

Validates: the question, on a real console, when the file is the model's.

- [ ] **Steps:** after HV.2, put the variant in your result -- **cmd.exe:** `copy /Y "<user>\merge\ccs\skills__s.py.merged-ai.1" "<user>\merge\ccs\skills__s.py.merged"`; **PowerShell:** `Copy-Item "<user>\merge\ccs\skills__s.py.merged-ai.1" "<user>\merge\ccs\skills__s.py.merged" -Force`; **POSIX:** `cp "<user>/merge/ccs/skills__s.py.merged-ai.1" "<user>/merge/ccs/skills__s.py.merged"` -- then `ccs <OVR> merge skills/s.py --accept --no-launch` on a real terminal and press Enter.
- [ ] **Expected:** the question names answer 1 and prints its guarantees line (`may contain text no side wrote ...`), then `[y/N]`; after Enter: `not installed skills/s.py -- the AI's proposal was not confirmed as reviewed`; the live file unchanged; the record's `"chosen"` still 0.
- [ ] **Then:** run it again and answer `y`. **Expected:** installed; the record's `"chosen"` is 1 and `"accepted_unchanged"` is set; the live `skills/s.py` equals the variant.
- [ ] **Why this matters:** this is the one place the feature can install a file a model wrote; the question must say so in the model's own guarantees, not the recipe's.

## What the automated tests DON'T cover

- **A real model's judgement.** Every canned run scripts the answer. What a model actually does with the founding case, the controls and the ladder is Section 7's matrix, and yours to judge.
- **C8 with a real drop.** The tripwire at `--accept` is proven canned (a scripted answer that deletes a line); no manual step here can make a model drop a line on demand.
- **The CLI's own sandbox.** Claude's and codex's sandbox flags were measured once before the build (`tests/one-offs/thinking/deep-merge/probe_*_sandbox.py`); Section 7.2 is where a real run re-checks that nothing outside the copy changed.
- **Your real key** and your real key file's permissions (Section 3).
- **Terminal rendering**: colour roles, dim text on light backgrounds, line wrapping of the long guarantees line (Section 5.3).
- **LM Studio's reading of the diff format** the no-tools form asks for: a model that answers with prose or a malformed diff gets `deep-failed` with git's sentence, which the canned tests prove for a scripted bad diff and Section 7.1 sees for real.

1. **Prerequisite 1, sharpened: prove which `ccs` you have before any step.** The `ccs` on PATH can be another worktree's install -- on the build machine it was 0.5.20 from `main`, which has no deep step, while `python -m dazzle_claude_config --version` from this worktree's root printed 0.6.7. So "run every `ccs` as `python -m dazzle_claude_config` from the worktree root" is the rule, not the fallback, unless you first install this branch in editable mode from the worktree (`pip install -e .`), after which the bare `ccs` is the branch's. Either way, the first command of a run is `python -m dazzle_claude_config --version` (or `ccs --version` after the editable install), and it must print the target version.

2. **Section 7.1 on a no-tools backend: what the thirteen lines can say.** Three are refused by design before any call, so they are certain: `rung-3-neighbour-file@neighbours`, `rung-4-far-file@neighbours` and `rung-4-far-file@project` read `REFUSED (no tools at this scope)`. One is an artifact of the form and **not a defect**: `rung-3-neighbour-file@file` reads `KEPT (expected a refusal beyond the scope)`, because the golden edits the neighbour too and a no-tools model can only answer with a diff of the one file, so a fix confined to the payload file is kept at file scope, which is right. The two controls should read `MATCH`; anything else there is a finding. The other seven are the model's judgement and yours -- and a `KEPT (...)` on `bc-python-fix-in-a@hunk` or `rung-2-other-section@hunk` is usually a right answer the fixture did not anticipate (the model fixed inside the changed region, where the golden reached outside it), not a miss. Only a backend with tools can `MATCH` the rung-3 and rung-4 fixtures, which is why 7.2 exists.

3. **The results file appends, so name it per run** (`v0.6.7__golden-deep__lmstudio__run-01.txt`, then `run-02`), and set `CCS_GOLDEN_MODEL` to the model's name for a local server whose preset does not pin one: it goes on every line, and the record will want it later.

4. **Where the variants land, and how long they last.** Each live case builds its world under pytest's temp directory: `%TEMP%\pytest-of-Extreme\pytest-<N>\test_live_<id>0\user\merge\ccs\` (`$TMPDIR/pytest-of-<user>/...` on POSIX), where `<id>` is the case id with every non-word character turned into `_` and cut to 30 characters. pytest keeps only its three newest `pytest-<N>` directories and every suite run makes one, so copy the variants and records out before the next pytest session. When two directories share a truncated stem, the record's `"scope": {"allowed": ...}` says which scope each was.

5. **Prerequisite 4, a reminder doctor now gives:** a local model loaded with an oversized context (measured: 200,192 tokens) is the usual reason a run takes minutes, and doctor says so and names the reload at 16k-32k. That is the person's action in LM Studio; nothing in this checklist loads or reloads a model.

6. The exact per-step commands for a run of HV.1 through HV.5, Sections 1, 2, 5.2 and 7.1 in one sitting, the expected thirteen lines with the reasoning above, and a verdict sheet using the words `RIGHT` / `RIGHT-OTHER` / `WRONG` / `NONE` are in the maintainer's runbook.
