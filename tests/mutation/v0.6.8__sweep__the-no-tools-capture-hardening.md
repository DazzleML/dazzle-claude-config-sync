# Mutation sweep: the no-tools capture hardening (unit of the deep-merge slice, #64)

The uncommitted 0.6.8 unit under review: `_apply`'s `--recount --unidiff-zero` relaxation on `git apply`, the `_HUNK_LINE` detector that tells a headers-only "nothing to change" diff from a real hunk, and the backend's raw reply being kept beside its variant (or under the unnumbered name) via `airecord.reply_path`. This sweep is diff-scoped to those moves across `aideep.py`, `airecord.py`, and `cli.py`.

**Generation-mode caveat, stated plainly because it affects how much this sweep should be trusted:** the mutation ideas were supplied directly in the dispatch prompt, by an author who had already read the tests closely enough to name exact assertions (`report={"hunk": [...]}`, the `kept.is_file()` check, `reply_path`'s exact name shape). I additionally read all three test files' diffs in full before writing the spec, to prepare the red-green audit that came first in this same run. Per the `/test-mutation` skill's generator contract, that makes this a **self-check** run, not the fresh-context mode the report tables normally assume -- the mutants were not blind to what the suite checks, so a kill here is weaker evidence than a fresh-context kill would be, and this sweep is barred from writing `equivalents.md` on that basis. It is still useful for what it does show: whether the specific failure shapes the diff invites are in fact caught, and it did surface one real gap (M6) that neither the red-green audit nor the golden fixtures had covered.

## Triage

| ID | Verdict | Reasoning |
|---|---|---|
| M6 | **killable** | No fixture in the golden set (`_Tools.invoke` / `_NoTools.invoke` in `test_golden_ai_deep.py`) ever returns a `Response` with `status="failed"` (`resp.ok` False) from inside `deep_step` -- every canned fake always answers `"answered"`. So nothing in the three killer files exercises the early-return branch this mutant touches, and the reordering is invisible to the current suite. It is a real gap, not equivalent: `Response.text` defaults to `""` on a failed response (`_vendor/ailib/types.py:174`), so under the mutant a backend failure (timeout, unreachable, refused by the transport) now creates an *empty* `<label>.merged-ai.deep-reply.txt` on disk, and because `out.reply` is set before the early return, `cli.py`'s `deep-failed` branch prints `reply: <name> -- what the model answered, kept beside your result` pointing at that empty file -- actively misleading, not harmless. The killing test would be: monkeypatch a fake backend whose `invoke()` returns `Response("failed", error="boom")`, call `deep_step`, and assert `airecord.reply_path(merged)` does not exist and `out.reply is None`. |

**Per this run's explicit instructions, the killing test above was not written and no production source was touched beyond the harness's own apply/restore window.** This is a deliberate deviation from `/test-mutation`'s normal "close the loop now" step (§7), noted rather than silently followed -- the gap is real and should get a test in a follow-up unit, but that is for the maintainer or a subsequent implement pass to do, not this verify run.

## Why no round 2

The skill's refinement-round trigger (>=1 killable survivor) is conditioned on feeding the new assertion back into a second generate+sweep round. Since writing that assertion was out of scope for this run, a round 2 would just re-run the same 10 mutants against an unchanged suite and reproduce the identical result -- it would not be a real refinement round, so it was skipped rather than performed as theatre.

## Caveats

A kill proves the suite noticed *this* change, not that it tests the right thing -- and **a clean sweep is evidence about the mutations tried, not proof of suite completeness.** This sweep additionally is self-check generation (see above): its 9/10 kill rate should be read as "the specific ideas this diff invited are covered, bar one," not as an independent measure of suite strength the way a fresh-context sweep's score would be.
